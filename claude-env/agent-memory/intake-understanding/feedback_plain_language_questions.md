Ask clarifying questions in PLAIN, non-technical language. Frame around what the user actually experiences ("the app changes my exercises too much", "weights look wrong"), NOT code internals (blacklist, validator loop, role tables, per-rep constants, ±10-min gate).

**Why:** In the generation-prompt-overhaul intake (2026-07-01) my first question round was too technical; the coordinator had to re-ask everything in plain language before the user could answer. The user also names problems by lived symptom, not mechanism (their only concrete complaint was "exercises or weights are off").

**How to apply:** Do the deep code/mechanism analysis for MYSELF (it grounds the briefs), but translate every user-facing question into plain terms. Lead with the symptom, offer concrete either/or choices, keep jargon out. Reserve the mechanism detail for the outcome-only briefs the orchestrator reads, and even there keep it outcome-first. Relatedly, the user decides by outcome preference ("reject or modify", not "advisory") — give them plain product choices, not architectural ones.
