Two non-obvious, load-bearing facts about the AiRepository generation seam (`generateAdaptedProgram` + `buildPrompt`). This is the SAME hot seam touched by v1.10.0 (B08/B09/B10) and v1.10.1 (G1); future waves here should know these.

**1. Wall-clock is BOUNDED, not infinite — but the bound is ~8 min and feels infinite.**
OkHttp `callTimeout(240s)` (NetworkModule) bounds every AI call, so a true infinite hang is impossible. BUT the generation request is NON-STREAMING with `ClaudeRequest.maxTokens=16384` (B10 raised it 8192→16384). A verbose attempt can need MORE generation time than 240s → callTimeout fires → `withAiRetry(maxAttempts=2)` retries IMMEDIATELY with no backoff → ~2×240s ≈ 8 min burned on a SINGLE attempt before any error surfaces. maxTokens and callTimeout are COUPLED: raising one without the other re-creates this. Do NOT change either casually.
**Why:** the v1.10.2 "Generate hangs on Attempt 2 of 3" bug. Attempt 1 (concise) succeeded; attempt 2 (prompted to "ADD work to all 5 days") was the verbose one that stalled. The eventual error reaches the UI via a one-shot Snackbar + STARTED-scoped collectors, so a user who navigates away (e.g. to Prompt Log) misses it and sees a frozen "Attempt 2 of 3".
**How to apply:** when touching generation reliability, bound the wall-clock INSIDE AiRepository (e.g. `withTimeout` around the loop) and surface a clear error via the existing onFailure path; flag any UI-layer error-durability gap rather than fixing it in the seam.

**2. The per-day time-budget gate vs. the volume caps is a NARROW but real tension — resolvable, NOT a structural impossibility.**
The strict per-day gate accepts only target±10 (e.g. 40–60 for a 50-min target). Hypertrophy days the model produces land 34–39 min because it uses SHORT rest (45–90s) when ≤120s is allowed, and tops out near the ~18–20 working-set cap. Verified with the authoritative `WorkoutTimeEstimator` on the captured plan: bumping rests to 120s moves the 5 days from 38/34/34/39/37 → 46/42/39/49/47. So REST alone clears the 40 floor for 4 of 5 days; the tightest day (17 sets, 6 exercises) reaches only ~39 even at rest@120 and needs one extra set/rep/exercise (still within ≤20 sets / ≤7 exercises Intermediate) to clear it.
**Why:** intake flagged a possible caps-vs-50-min structural contradiction that would force escalation. Diagnosis showed it is NOT impossible — the model just leaves the rest+volume levers unused.
**How to apply:** H3-class under-fill is steerable PROMPT-SIDE but needs BLUNT steering (see fact 3). No escalation/gate-relaxation needed.

**3. LIVE-MEASURED (2026-06-27, real Anthropic key) — supersedes the "should work" guesses above:**
- **v1.10.3 shipped H1+H3+H2 and REGRESSED generation (→ H4).** H1's `isTransientGenerationError` (SocketTimeout NON-retryable) made a generate timeout TERMINAL with nothing logged (PromptLog writes only AFTER a response). Full-program generation + whole-week regen now fail with "AI request timed out" under a working network; single-day regen (small) still works. Weekly COACH summary is FAST (~8s/250 tok) — NOT a batch victim; "weekly broken" = the weekly PROGRAM generation, not the summary.
- **Latency:** full-generate is ~58–179s and HIGHLY variable for the SAME prompt (attempt-2/rejection-feedback prompts are the slow tail, ~179s — right at the 180s OkHttp read timeout). Non-streaming ⇒ time-to-first-byte ≈ full generation time ⇒ crosses the 180s readTimeout. **Fix = STREAMING** (validated live: continuous content_block_delta + ping events, so a 180s INTER-EVENT readTimeout never fires on a healthy long generation while a genuine stall still trips it; reconstruct text+stop_reason from the SSE).
- **H3 soft steering does NOT work on the live model: 8/8 generations under-filled (30–44 min, never all-in-window).** The model keeps standard SHORT isolation rest (60–90s) and ~16–18 sets despite "raise rest toward the band max".
- **CRITICAL steering nuance (live-tuned 2026-06-27): "clear the floor / don't chase 50" BACKFIRES** — it makes the model MINIMIZE volume (14–17 sets across 4–5 ex) → under-fills (0/4 in-window). What WORKS (4/5 in-window, days cluster 42–48): force BOTH levers explicitly — recommendedRestSeconds=120 on EVERY hypertrophy set INCLUDING isolation AND a FULL ~19–20 working sets across ~6 exercises ("do NOT stop at 15–17 sets"), and AIM ~46–47 (a few min ABOVE the floor), NOT "minimally clear 40". The SET-COUNT must be pushed, not just rest. 20 sets + 120s rest + 6 ex ≈ 47 min (cap-determined, independent of the 50 target).
- **Reliability = streaming + retries, not perfect per-attempt steering:** ~80% per-attempt in-window ⇒ the 3-attempt loop (now retrying WITHOUT timing out, thanks to streaming) makes end-to-end failure <1%. The ~46–47 landing is fixed by the 20-set/120s cap, so it only clears a floor of ≤~44: **session targets >~55 min (floor T-10 > what the cap yields) are a genuine structural wall → escalate, do NOT chase.** User's profile is 50 min (works). validateProgram allows ≤120s rest and ≤~20 sets; gate stays strict; pure prompt-side.

**4. v1.10.4 STREAMING REGRESSED with an ANR (→ H5, fix = v1.10.5).** The SSE fix consumed the `@Streaming` ResponseBody with a BLOCKING `okhttp3.ResponseBody.string()` inside `AiRepository.sendStreaming`, but generate is launched from viewModelScope (`Dispatchers.Main`) and the suspend call resumes on the caller's dispatcher → the multi-minute body read ran ON THE MAIN THREAD → ANR ("isn't responding"), NOT a thrown exception (so the UncaughtExceptionHandler crash-log AND the on-completion prompt-log were both EMPTY). On-device trace (Waydroid) bottomed out in `Looper.loop`/`Http2Stream.waitForIo`. Fix: wrap stream consumption in `withContext(Dispatchers.IO)`. **PROCESS LESSON (load-bearing): `./build.sh test` (JVM unit) CANNOT catch an Android main-thread ANR — v1.10.4 shipped green-unit + my own live-API curl checks (which run off-device, so never hit Main) and STILL ANR'd on device. For any change to threading / the network call path / dispatchers, on-device (Waydroid) verification is REQUIRED before ship; unit-green is necessary but NOT sufficient.** Note: the launch-time weekly AUTO-adaptation runs on a background coroutine and was NOT affected — only the foreground viewModelScope generate paths ANR'd.

**5. G2 round (post-v1.10.5, live-measured 2026-06-27 by the orchestrator): the EFFICIENCY problem and the GATE-SATISFIABILITY problem are SEPARATE; the efficiency fix solves the first but EXPOSES the second as a STRUCTURAL WALL.**
- *Efficiency root cause (fixed, prompt-side):* generation is a NON-thinking `claude-sonnet-4-6` call (no `thinking` param), but the base prompt demanded heavy "silent" reasoning ("reason silently / COMPUTE every day silently / SELF-CHECK before output") → the model EXTERNALISES it as visible output, generating near the full 16384-token budget every attempt (~4.5 min/attempt at ~60 tok/s) and on attempt 1 often rambling prose ("I'll…") to NO usable JSON. The blunt "lead-with-JSON" steering only reached the model on RETRY. FIX (the G2 change, AiRepository.kt buildPrompt only, prompt-text): blunt JSON-only OUTPUT directive on EVERY attempt + TERSE one-clause notes (effort+progression kept; ~280→~55 chars) + brief ≤2-sentence rationale + removed the "narrate/compute silently" invitations (volume recipe kept byte-for-byte). LIVE RESULT: every attempt now leads `{`, completes (end_turn), ~34s, ~2200 output tokens (was ~10500). A full 3-attempt loop's gen time ≈ ~100s, comfortably inside the 360s deadline. Speed/ramble/truncation = SOLVED.
- *Gate-satisfiability (NOT fixable under Option A — STRUCTURAL):* even with the efficiency fix, the model RELIABLY leaves exactly ONE (rotating) day OUT of the strict ±10 window — almost always a big OVERSHOOT (62–90 min vs 60 ceiling), occasionally an undershoot. Direction-aware retry feedback ("TRIM day N") fixes the flagged day but the model then overshoots a DIFFERENT day → WHACK-A-MOLE. Live: **0/3 full 3-attempt loops produced an all-5-days-in-window plan; 9/9 attempts had ≥1 out-of-window day.** So the run still SAVES NOTHING for the 50-min/5-day Hypertrophy profile.
- **CORRECTS prior fact 3's optimism:** "~4/5 in-window per attempt ⇒ 3-attempt loop succeeds <1% failure" was WRONG — the OUT day ROTATES, and the anti-under-fill recipe (force ~20 sets @120s rest, AIM 46-47) pushes every day near the ceiling so the highest-rep day tips over; pushing one day down induces overshoot elsewhere. 20 sets@120s sits near the top of a 20-min-wide window → little margin → P(all 5 in-window) is low and does not converge in 3 tries.
- **DECISION: this is the brief's escalation condition (strict gate + model behaviour structurally unsatisfiable for this profile). ESCALATED to the user — did NOT touch the gate/deadline/attempts/add salvage. The efficiency fix is independently real & shippable as a speed/reliability improvement, but does NOT by itself make full-generation reliably SAVE.** Any further attempt to make the gate satisfiable (prompt-side anti-overshoot "no day may exceed ~55 min" refinement, or reconsidering Option B auto-trim / C wider window) is a USER decision. Harness caveat: simulated with EMPTY history (new user) — faithful for time-budget behaviour, real history/blacklist + in-app Retrofit @Streaming path not exercised (no Waydroid).

**6. G2 RESOLUTION (user reversed "no-salvage" → Option B; live-measured 2026-06-27). Final shippable design = efficiency fix + deterministic auto-trim salvage; adaptive thinking TESTED LIVE and REJECTED.**
- *Option B auto-trim (SHIPPED):* when an attempt yields an otherwise-valid plan that fails the gate ONLY because some day(s) ESTIMATE OVER the ceiling (no under-day, no other deterministic failure), salvage it deterministically. New pure helper `trimOverflowToWindow(exercises, target, lockedDays)` trims each over-day, re-estimating after each step, with ladder **REST → SETS → REMOVAL**: (1) lower recommendedRestSeconds of the current highest-rest exercise by 15s toward a 60s floor (never <60, never > original); (2) drop a set off the trailing non-primary exercise (sets>2); (3) remove a trailing non-primary exercise IF its muscle is still covered (MuscleClassifier), day stays ≥floor, ≥4 exercises remain. Stop at floor≤est≤high; return null if any over-day can't reach the window (→ normal reject). Loop integration: FALLBACK only — clean model plan saves preferentially; track the SMALLEST-overshoot overshoot-only attempt; at the terminal reject point, trim that candidate, re-serialize, run validateProgram (overshoot attempts were never LLM-reviewed), save if accepted. Honest note appended to rationale. **REST-FIRST is load-bearing: rest is the dominant time term; sets+removal-only salvaged 3/4 live loops, rest→sets→removal salvaged 4/4** (rest-reduction reclaims the most minutes with zero loss of exercises/sets/coverage, stays in the hypertrophy 60–120 band).
- *Adaptive thinking — TESTED LIVE, BUST, DO NOT ENABLE on the generation call:* hypothesis was a private thinking channel would stop ramble + let the model iterate the per-day math (kill the whack-a-mole). LIVE on `claude-sonnet-4-6` + `thinking:{type:"adaptive"}` + max_tokens 32000: **0/3 converged, ~522s/gen (ALL over the 360s deadline), the model spent the ENTIRE 32000-token budget on thinking and emitted vis~0 / NO JSON, ~$0.50/gen.** On this very large constraint-heavy prompt adaptive thinking thinks unboundedly and STARVES the visible JSON; 32000 wasn't enough headroom and raising it only makes it slower/costlier. Opus not tested (spend limit; a pricier model that thinks MORE has no path to better). **Conclusion: keep the generation call NON-thinking.** (The stream parser already ignores thinking_delta — only accumulates text_delta — so a future thinking experiment won't corrupt the plan path; a defensive H4 parser test was kept.)
- *Whack-a-mole is NOT fully solvable prompt-side on sonnet;* the strict ±10 gate is satisfied in production by the 3-attempt loop + the deterministic auto-trim salvage, NOT by perfect model convergence (0/3 clean even with thinking). The 20-set/120s recipe parks days near the ceiling so one rotating day overshoots; trim fixes it deterministically.
- *Build/test harness note:* `buildPrompt` is private; to render the REAL prompt for live A/B I invoked it via reflection on an `Unsafe.allocateInstance(AiRepository)` (its injected deps are never touched by buildPrompt) — package-level helpers (trimOverflowToWindow, dayDurationFeedback, parseClaudeStream) are directly testable. Live-API verification ate the key's credit balance mid-task once (~35 full gens) → be FRUGAL: each live call must decide something; render the real prompt and reuse captured plans rather than re-generating.
