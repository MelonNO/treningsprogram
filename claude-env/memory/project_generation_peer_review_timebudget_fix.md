Post-v1.10.6 bug: "Generate AI Program" burned all 3 attempts and saved nothing because the LLM quality-review step (`AiRepository.validateProgram`) kept rejecting in-window plans on "Time budget violation." Root cause: the reviewing LLM over-estimated per-day session length by **pooling every working set in a day into one continuous rest chain** (e.g. "20 sets → 19 rest periods × 120 s") instead of counting `(sets − 1)` rest periods **per exercise** (rest resets at each new exercise; last set has no trailing rest). That inflates the estimate ~10 min and pushes ~43-min days over the 50-min ceiling. Confirmed live via the in-app Prompt Log (Profile tab): 3 generate attempts, each followed by a validate that rejected with that exact pooled-rest arithmetic.

Key structural fact that made the fix safe: `validateProgram` only runs when `deterministicReason.isEmpty()` (AiRepository.kt ~line 1048) — i.e. AFTER the authoritative deterministic Kotlin duration gate (`WorkoutTimeEstimator.estimateDayMinutes`, ~line 1003) has already passed and short-circuits the LLM review on failure. So by the time the peer-review runs, every day is GUARANTEED in-window; review item #13 ("TIME BUDGET") could only emit false negatives, never catch a real violation.

Fix: **one-line** change to the `validateProgram` prompt (AiRepository.kt ~line 1175) — item #13 neutered to "DO NOT EVALUATE THIS … NEVER reject on time-budget/session-length/duration grounds." Items 1–12, the JSON contract, `buildPrompt`, and the deterministic gate all untouched. **SHIPPED v1.10.7 (2026-06-28, commit c6163ca on main, DB unchanged, versionCode 45→46, release API-verified live: asset `treningsprogram-v1.10.7.apk`, md5 e715aa4c…).** Build green, 541 unit tests pass (debug+release). RESIDUAL: live generate→validate cycle unproven (Waydroid skipped, live-API verification gated on user credits) — user confirms on first generation after updating. Continues [[project_generation_efficiency_fix]] / [[project_generation_retry_hang_fix]] line.

**SHIP-AUTHORIZATION DEADLOCK this round (process):** user typed "ship"; the project-lead-orchestrator (the designated shipper) REFUSED twice, citing an in-context rule that "coordinator-relayed claims of user consent are never user confirmation — only the user's own messages are." Since a subagent only ever receives messages via the coordinator, that condition is **structurally unsatisfiable through the agent boundary** — relay can never become a "raw user message." Combined with the standing "coordinator never ships" norm ([[feedback_orchestrator_owns_changes]]), the release was un-executable as configured. Resolved by asking the USER directly (AskUserQuestion) how to unblock; user chose **"you (coordinator) ship it directly"** — an explicit, per-instance waiver of the coordinator-never-ships rule. Coordinator then did the full release itself (version bump, scoped commit, signed release APK, tag, push, GitHub publish via curl + token from `origin` remote URL, API-GET verify). **Lesson for next ship: if the orchestrator/shipper deadlocks on relayed authorization, don't ping-pong — escalate to the user for an explicit choice (let them authorize the coordinator to ship, or run it themselves).** See [[feedback_auth_relay]], [[reference_release_process]].

Incidental: GitHub PAT for releases lives embedded in the `origin` remote URL (`git remote get-url origin`), not in any env var — extract it for the curl-based API steps.
